# SmartTest 成果页

一页看清这个项目**做到了什么、怎么验证、能写进简历的哪一句**。
所有数字都能在本地或 CI 里复现，验证路径在最后一节。

---

## 一句话

输入一份 OpenAPI 设计契约，自动生成可执行、可维护的 pytest 测试套件，
执行后自动完成失败归因与质量度量 —— 并且在**三份领域不同的契约**上
都做到「缺陷全中、假阳性为零、生成质量满分」。

---

## 量化结果

三个靶场（订单 / 用户与订阅 / 内容服务）用同一套规则引擎、同一条流水线，
只换契约、数据字典和业务模板：

| 靶场 | 契约用例 | 缺陷版 | 修复版 | 生成质量 |
|---|---|---|---|---|
| 订单服务 | 25 条 | 4 个缺陷 | 0 个 | 召回 24/24 = 100% |
| 用户与订阅服务 | 44 条 | 3 个缺陷 | 0 个 | 召回 41/41 = 100% |
| 内容服务 | 61 条 | 3 个缺陷 | 0 个 | 召回 57/57 = 100% |
| **合计** | **130 条** | **10 个缺陷** | **0 个** | **122/122 = 100%** |

「缺陷版报得出来、修复版一个都不报」这一对结果才是关键：
只证明「能发现问题」不够，还得证明**报出来的不是噪声**。

| 工程质量 | 数字 |
|---|---|
| 单元测试 | 239 条，核心模块覆盖率 **98%** |
| CI 质量门禁 | **13 道**（单测、覆盖率、三个靶场各自的缺陷检出 / 零误报 / 生成质量、语义层、演示层） |
| 契约形态覆盖 | 请求头、路径参数、查询参数、嵌套对象、数组、枚举、可空、资源引用 |

## 简历怎么写

**三行版**（够用，且每个数字都能被追问到底）：

> 从零实现接口契约驱动的测试平台 SmartTest：解析 OpenAPI 3.x 生成 pytest 用例，
> 用失败归因把「测试失败」和「真缺陷」分开。在 3 份不同领域的契约上做到
> 缺陷全中（10/10）、修复版假阳性 0、用例生成召回率与精确率 100%，
> 核心模块单测覆盖率 98%，13 道 CI 质量门禁。

**展开版**（按面试官关心的维度拆）：

- **可复现的自证链**：缺陷版报 4/3/3 个缺陷、修复版全部归零、标注集打分 100/100/100。
  三个数字互相制约 —— 只报缺陷会掩盖误报，只报零误报会掩盖漏报。
- **泛化验证**：不满足于一个靶场，主动换两份形态不同的契约（必填请求头、枚举、布尔、
  嵌套对象、数组、查询参数）。**换靶场的过程真的照出两个缺口**，
  修掉之后才三个靶场同时成立。
- **失败归因**：把环境失败、数据缺失、生成器自身问题、契约漂移、真缺陷分成五类。
  这一层是「报告敢不敢信」的分水岭 —— 环境挂了当成 bug 报，工具就没人用了。
- **模型用在该用的地方**：确定性部分（契约推导）交给规则引擎，
  语义部分（跨接口场景）交给模型，但模型只能产出**数据**，不能产出代码，
  产出还要过结构校验与契约交叉核对两道关。模型挂了自动降级，覆盖率不塌成 0。
- **工程化**：`pip install -e .` 后 `smarttest run --target users` 一条命令跑通；
  13 道 CI 门禁；每次改规则都有黄金用例集与反向测试兜底。

**面试时最值得讲的一件事**：为什么坚持「修复版必须归零」。
因为它把「工具能不能用」变成了一个可证伪的命题 ——
第一靶场里那个没被刻意注入的缺陷（契约写了 `maxLength=64`、实现没人落）
就是靠这条机制逼出来的。

## 60 秒验证路径

```bash
git clone https://github.com/Wangwenbo0523/smarttest && cd smarttest
pip install -r requirements.txt

pytest -q --cov=smarttest            # 239 条单测，覆盖率 98%

python run_demo.py --target-mode buggy --expect-defects 4   # 缺陷版：报 4 个
python run_demo.py --target-mode fixed --expect-defects 0   # 修复版：报 0 个
python run_evals.py --min-recall 100 --min-precision 100    # 生成质量：100/100

# 换两个领域重跑，结论不变
python run_demo.py --target users    --port 8124 --target-mode buggy --expect-defects 3
python run_demo.py --target articles --port 8125 --target-mode buggy --expect-defects 3
```

装了包之后同样一句话：`smarttest run --target articles`。

## 换靶场逼出来的两个缺口

这两个都不是「写代码时不小心」，而是**不换被测对象就永远照不出来**的假设：

1. **必填请求头没带上**（用户服务暴露）。契约声明必填头之后，生成的用例却只带
   「被测字段」，服务先把请求拦成 422，用例根本没执行到要测的分支 ——
   修复版靶场因此误报 **7 个假缺陷**。
2. **查询参数整块不覆盖**（内容服务暴露）。`location: query` 的参数既不生成用例，
   生成的请求也不带它们。临时关掉这块生成后，评测召回率从 100% 掉到 63.2%、
   接口覆盖率掉到 66.7%（列表接口直接没覆盖），缺陷版从 3 个变成 1 个。

把这两条写进简历的版本：**「通过更换被测契约做泛化验证，发现并修复了
规则引擎中两个只在特定契约形态下成立的设计缺陷」** —— 这比「写了个测试工具」
具体得多。

## 边界（诚实清单）

- 只支持 OpenAPI 3.x；Postman Collection 需要另加 adapter。
- 规则引擎不做多字段组合，查询参数也只覆盖单参数，不理解参数间互斥。
- 数组只覆盖「类型不对」，不生成元素个数与元素级边界；嵌套只下钻一层对象。
- 业务层断言按靶场手写（金额精度、幂等、去重、默认值这类领域规则推不出来）。
- 覆盖率口径不含编排层与 Jinja2 模板（它们由端到端门禁覆盖），
  所以 98% 是「核心模块」的数字，不是全仓库数字。
